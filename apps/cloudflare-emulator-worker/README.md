# Gateway público del emulador hidráulico

Este Worker expone la demo de `water-network-scale-v1`. Sin configurar `ACCESS_TEAM_DOMAIN` y `ACCESS_AUD`, el modo actual emite capacidades anónimas firmadas y temporales, limita el tráfico y asocia sesiones a esa capacidad; esto **no identifica visitantes** ni impide toda automatización. Cuando ambas variables están configuradas, el gateway exige una aserción JWT válida de Cloudflare Access para iniciar sesiones y cada ruta API/WebSocket (salvo health e interfaz interna D1); la identidad verificada queda vinculada al propietario de la sesión y el navegador no recibe bearer. Para comprobar grants por usuario/gemelo, reenvía al API de control la aserción y solo la cookie `CF_Authorization` por una cabecera interna; la sesión no se copia a Containers ni se registra. Para llamadas internas de Fractal, el Worker emite una capacidad HMAC de audiencia separada y duración corta. El cliente debe enviar cookies de Access con credenciales incluidas. El servicio es un modelo virtual, sin conexión a un PLC físico.

**Estado de transición:** Cloudflare Access ya protege la Gallery en `digitaltwin.arvantti.online`, pero el hostname first-party de API todavía no está configurado para Access y este Worker no se ha actualizado con la rama de autorización. El cliente elimina bearers heredados; en modo Access usa solo la cookie HttpOnly para API/WebSocket. Las demos anónimas sin Access aún usan bearer en memoria y clave de recuperación en `localStorage`. La protección de Gallery por sí sola no autentica este gateway ni aplica permisos de usuario/modelo/acción. No activar el modo en producción hasta configurar/probar Access en el hostname API, desplegar la autorización y validar sesiones/WebSocket y la transición de estudios anónimos existentes.

## Arquitectura y límites

- Pages aloja la galería; este Worker es el único endpoint público de la API. No publicar URLs de Containers.
- El gateway permite solo `water-network-scale-v1`; D1 conserva perfiles, historian, estudios, auditoría y checkpoints. SQLite es únicamente para desarrollo local.
- Las rutas de API requieren una capacidad Bearer anónima emitida por `POST /api/demo/session`; `/api/health` es público y limitado. WebSocket usa dos subprotocolos: el token viaja al Worker y el Container recibe únicamente `arvantti-demo`.
- Las clases de Container usan la API nativa de Containers dentro de Durable Objects, con `scheduling_policy: durable_object`, imagen fijada por digest y `standard-1`. El acceso a Internet está deshabilitado. El HTTPS interceptado al Worker admite solo el bridge D1, la API PLC autorizada y las rutas internas exactas de Cosimulación; estas últimas requieren `COSIMULATION_INTERNAL_TOKEN` y el Worker enruta directamente a los Durable Objects engine/modelo. El bearer se valida en el relay y se elimina antes de llegar a cada Container. No cambiar la política de scheduling ni exponer Containers.
- La capacidad PLC vence a las 12 h. La sesión vence a las 2 h, cada visitante puede crear 2 y el gateway limita a 10 sesiones retenidas simultáneamente. Se eliminan datos transitorios asociados a visitantes vencidos al emitir nuevas capacidades. La excepción son los estudios archivados: migración `0005_saved_studies.sql` los conserva hasta borrado explícito y mantiene la identidad anónima necesaria para recuperarlos desde el mismo navegador. La biblioteca limita cada propietario/planta a 50 estudios, 50 versiones por estudio y 50 MB acumulados. La clave de recuperación queda solo en `localStorage`; no hay recuperación entre dispositivos ni tras perder los datos del sitio. Diseño y rutas: [`docs/architecture/durable-study-library.md`](../../docs/architecture/durable-study-library.md).
- Límite Worker: 10 emisiones/min/IP, 120 llamadas API/min/IP y por capacidad, y 10 solicitudes Fractal/min/IP y por capacidad. Mandos WebSocket PLC: hasta 30 mensajes/s, una conexión PLC operativa por sesión. La API detiene la simulación PLC al cerrar la conexión en pruebas locales; verifica ese comportamiento a través del relay WSS antes de darlo por garantizado en Cloudflare.
- Los estudios PLC-backed (proyección horaria y cosimulación) solo se reenvían desde una sesión propia de la capacidad anónima; los resultados son de solo lectura. Si no está configurado `COSIMULATION_INTERNAL_TOKEN`, el workflow despliega `COSIMULATION_RELAY_ENABLED=false`, Fractal no recibe endpoint de engine y la cosimulación permanece deshabilitada (aunque haya quedado un secreto viejo en Cloudflare). Con secreto válido, el Worker habilita únicamente los destinos internos allowlisted engine/modelo; nunca publica URLs directas de Container. Persisten pendientes el despliegue autorizado, pruebas remotas y validación del modelo. Recomendaciones instantáneas y acciones de decisión/activación siguen bloqueadas. Perfiles editables se aíslan por capacidad anónima.
- `/_internal/d1` solo acepta el secreto de bridge. `/_admin/*` deniega por defecto; puede protegerse además con Cloudflare Access. CORS solo controla lectura desde navegadores, **no es autenticación**.

Los límites son defensas de abuso, no una garantía de costo máximo ni de continuidad. Vigilar consumo/cuotas y ajustar límites en Cloudflare después de medir carga real. La demo abierta permite a cualquier visitante anónimo que llegue al gateway crear una sesión hasta alcanzar las cuotas globales; si el presupuesto no admite ese riesgo, no publicar el endpoint todavía o añadir Turnstile/WAF.

## Recursos Cloudflare requeridos

- Workers Paid/Containers, Durable Objects y D1 habilitados; revisar costes, límites y compatibilidad en la cuenta antes de publicar.
- Cuenta/subdominio `workers.dev`; opcionalmente un hostname propio HTTPS para el gateway. No se asume que exista ningún dominio o recurso.
- GitHub Actions con un API token de privilegios mínimos, `CLOUDFLARE_ACCOUNT_ID` y los secretos/variables descritos abajo.
- Docker Buildx en Actions. El Worker no expone el Container directamente.

## Provisionamiento y despliegue

Desde la raíz del repo:

1. Provisionar D1: `pnpm --filter @twin/cloudflare-emulator-worker exec wrangler d1 create acueducto-emulator --config ../../wrangler.acueducto.jsonc`. Configurar localmente el identificador devuelto en `wrangler.acueducto.jsonc`; no copiarlo a documentación, capturas ni notas.
2. Configurar GitHub Actions secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `D1_BRIDGE_TOKEN` (aleatorio, 32 bytes o más) y `DEMO_TOKEN_SECRET` (aleatorio, al menos 32 caracteres). Opcionalmente, configurar `COSIMULATION_INTERNAL_TOKEN` (32–256 caracteres URL-safe aleatorios) para habilitar el relay privado engine/modelo; sin él, Cosimulación sigue bloqueada. Generarlo localmente con `openssl rand -hex 32` y pegarlo solo en GitHub Secrets, nunca en el repositorio, navegador, logs ni chat.
3. Configurar GitHub Actions variables: `D1_GATEWAY_ORIGIN` (origen HTTPS `workers.dev` usado por Container→Worker→D1), `CORS_ORIGINS` (orígenes exactos de Gallery) y `EMULATOR_API_DOMAIN` (hostname HTTPS first-party, por ejemplo `api.digitaltwin.arvantti.online`). Para activar Access en el Worker, configurar juntas `ACCESS_TEAM_DOMAIN` y `ACCESS_AUD`; el workflow exige también el hostname first-party. Crear una aplicación Access para ese API hostname usando el mismo IdP y la misma allowlist global que Gallery (SSO; no credenciales/login distintos por proyecto). No proteger el origen `workers.dev` con una aplicación Access: el gateway valida la aserción y rechaza ahí las llamadas públicas directas, mientras los servicios internos usan una capacidad de relay firmada. Proteger con una sola aplicación/política todo el hostname Gallery y también el alias Pages alterno; usar el mismo IdP/SSO para que el login sea común a todos los modelos, no por proyecto.
4. Tras el primer despliegue, configurar también la variable Pages `EMULATOR_API_URL` con el endpoint HTTPS público del Worker. El workflow Pages la compila como `VITE_EMULATOR_API_URL`; el parámetro `?api=` puede sustituirlo para pruebas. Sin esta variable, la HMI buscará la API en el origen de Pages.
5. Ejecutar manualmente `Actions → Deploy acueducto emulator → Run workflow` en `main`. El workflow valida placeholders, corre pruebas, aplica migraciones D1, carga secretos configurados y despliega Worker/Containers. Solo habilitar `COSIMULATION_INTERNAL_TOKEN` y desplegar los dos Containers nuevos tras autorización y validación del modelo. Para Pages, `Actions → Deploy` publica la galería con el endpoint configurado.
6. Comprobar `/_worker/health`, `POST /api/demo/session` desde el origen Pages, `/api/health`, crear sesión, conexión WSS PLC y espectador 3D, aislamiento con otra capacidad, perfiles, proyección Fractal de solo lectura y persistencia tras dormir/reiniciar Container. Probar cosimulación solo cuando el motor/modelo estén provisionados; sin ellos, verificar respuesta de indisponibilidad y cero frames publicados. Probar explícitamente cuotas, recuperación y eliminación de sesiones vencidas. No aceptar despliegue como validado hasta hacer estas pruebas con D1/Containers remotos.

El workflow se ejecuta solo a demanda, no con cada push. Los nombres/URLs placeholder son intencionales; el despliegue falla antes de publicar si `database_id` o los secretos no están configurados. Ninguna URL de Container ni credencial se debe incluir en JavaScript.

## Desarrollo local y validaciones

- Desarrollo local de FastAPI usa SQLite; no defina `TWIN_DATA_BACKEND`.
- `pnpm --filter @twin/cloudflare-emulator-worker typecheck`
- `pnpm --filter @twin/cloudflare-emulator-worker test`
- `pnpm --filter @twin/cloudflare-emulator-worker exec wrangler d1 migrations apply acueducto-emulator --local --config ../../wrangler.acueducto.jsonc` (incluye `0005_saved_studies.sql`)
- `pnpm --filter @twin/cloudflare-emulator-worker exec wrangler deploy --dry-run --containers-rollout=none --config ../../wrangler.acueducto.jsonc`
- El build completo de Container/despliegue requiere Docker Buildx y recursos/secretos Cloudflare reales.

Los checkpoints internos usan pickle comprimido y versión de esquema. Restaurar exige compatibilidad de clases/modelo. El Container puede dormir tras 10 minutos inactivo. La continuidad/retroceso, comportamiento de desconexión WSS, latencia, costos y recuperación requieren seguimiento en Cloudflare antes de presentar la demo como servicio confiable.
